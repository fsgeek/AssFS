## Root Cause Analysis

The problem lies in the **race condition** between session validation and session refresh in the `validateSession` function in `src/auth/session.ts`. Here's what happens:

1. **Long-running requests**: The upload endpoint (`src/api/uploads.ts`) can take up to 5 minutes to process large files
2. **Session refresh timing**: During these long uploads, if other requests from the same user occur (like periodic heartbeats, auto-saves, or background requests), they call `validateSession`
3. **Race condition**: The `validateSession` function has a critical flaw:

```typescript
export async function validateSession(token: string): Promise<Session | null> {
  const data = await cache.get(`session:${token}`);
  if (!data) return null;

  const session: Session = JSON.parse(data);
  const elapsed = Date.now() - session.lastActivity;
  if (elapsed > SESSION_TTL * 1000) {
    await cache.del(`session:${token}`);
    return null;
  }

  // Problem: Two async operations without atomicity
  session.lastActivity = Date.now();
  await cache.set(`session:${token}`, JSON.stringify(session), SESSION_TTL);
  return session;
}
```

**The Issue**: Between the `cache.get` and `cache.set` operations, there's no atomicity. If multiple requests validate the same session simultaneously:

1. Request A gets the session data
2. Request B gets the same session data  
3. Request A updates lastActivity and writes back
4. Request B updates lastActivity with a slightly different timestamp and overwrites A's write
5. Meanwhile, Redis's TTL countdown continues from the original session creation
6. If the upload takes longer than the remaining TTL, the session expires even though there was recent activity

## The Fix

The fix requires making the session refresh atomic. Here's the corrected `validateSession` function:

```typescript
export async function validateSession(token: string): Promise<Session | null> {
  const data = await cache.get(`session:${token}`);
  if (!data) return null;

  const session: Session = JSON.parse(data);
  const elapsed = Date.now() - session.lastActivity;
  if (elapsed > SESSION_TTL * 1000) {
    await cache.del(`session:${token}`);
    return null;
  }

  // Fix: Use Redis SETEX with GET to atomically refresh TTL
  // This resets the Redis TTL to the full SESSION_TTL duration
  session.lastActivity = Date.now();
  await cache.set(`session:${token}`, JSON.stringify(session), SESSION_TTL);
  
  return session;
}
```

Now let me analyze the critical bug. Looking at the code flow:

**In createSession():**
- Creates session with `lastActivity: Date.now()`
- Sets Redis key with TTL = SESSION_TTL (1800 seconds)

**In validateSession():**
- Gets session from Redis
- Calculates: `elapsed = Date.now() - session.lastActivity`
- Checks: `if (elapsed > SESSION_TTL * 1000)`
- Updates: `session.lastActivity = Date.now()`
- Re-sets Redis with TTL = SESSION_TTL

**The Bug:**

There are actually TWO related issues:

1. **Redis TTL vs. Session Validation Mismatch**: 
   - Redis key expires after SESSION_TTL seconds (1800)
   - But validateSession() checks if `elapsed > SESSION_TTL * 1000` milliseconds
   - This means: if Redis expires the key, validateSession() will get null and return null
   - However, the session validation check is ALSO checking elapsed time independently

2. **The Real Critical Bug - Race Condition with Redis TTL**:
   - When a session is created, Redis sets it with EX: 1800 (seconds)
   - Each time validateSession() is called, it re-sets the key with EX: 1800
   - **BUT** if the Redis key expires naturally (TTL reaches 0), the next validateSession() call gets null from Redis
   - However, there's a SECOND issue: the validateSession() function updates `session.lastActivity = Date.now()` AFTER checking expiry
   - This means the check `elapsed > SESSION_TTL * 1000` is checking the OLD lastActivity time

3. **The Actual Root Cause - Concurrent Request Issue**:
   - During a long-running upload (5 minutes), the middleware validates the session at the START
   - But if OTHER requests come in from the same user during the upload, they will call validateSession()
   - Each call updates `session.lastActivity = Date.now()` in the session object AND re-sets Redis
   - **HOWEVER**: there's a race condition where the Redis key can expire between validation and the next check
   - More importantly: if a request takes longer than the remaining TTL, the session expires
