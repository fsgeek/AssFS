**Q1: When you're working on a software project and your context resets (new session, context compression), what information do you find yourself spending the most effort rediscovering? What's hardest to reconstruct?**
The most effort goes into rediscovering:
1. **The "mental map" of the codebase**: How files relate to each other and where key logic lives. For example:
   - After a reset, I might forget that `auth.py` handles both JWT token generation *and* OAuth2 flows, or that `utils/logging.py` is where all logging configuration lives.
   - If I was in the middle of tracing a bug across 3 files, I’d have to re-find those files and re-establish the connections between them.
2. **State of in-progress changes**: If I was partway through implementing a feature (e.g., "add a new field to the User model and propagate it through the API"), I’d need to:
   - Re-find the files I’d already modified (e.g., `models/user.py`, `schemas/user.py`).
   - Recall what still needed to be done (e.g., "I updated the schema but haven’t touched the database migration yet").
3. **Assumptions or constraints**: For example:
   - "This project uses `async` SQLAlchemy, so I can’t use synchronous database calls."
   - "The frontend expects snake_case keys, but the backend uses camelCase internally."
   - "This function is called by a background task, so it can’t block for too long."
   These are often scattered across files or buried in comments, making them easy to miss after a reset.

The hardest to reconstruct is **the "why" behind decisions**. For example:
- Why was a certain design pattern chosen (e.g., "Why is there a `UserService` class instead of putting logic directly in the route?")?
- Why was a bug fixed in a specific way (e.g., "Why does this function have a `try/except` for `IntegrityError`?").
- Why certain files exist (e.g., "Why is there a `models/user_base.py` and a `models/user.py`?").
This often requires re-reading Git history, comments, or even the user’s past messages.

     - The database model (`models/user.py`).
     - The Pydantic schema (`schemas/user.py`).

5. **External dependencies**:
   - A script in `scripts/backup_db.py` is only run manually by the user, but there’s no note in the file about when or why it’s used.

**Q4: When you navigate a filesystem — listing directories, searching for code, finding files — what feels natural and what feels like a workaround? What would you do differently if you weren't constrained to a directory tree?**
**What feels natural:**
1. **Directory structure for broad organization**:
   - Grouping files by domain (e.g., `users/`, `orders/`, `auth/`) makes it easy to guess where to look for related code.
   - Standard directories like `models/`, `services/`, `routers/` in a FastAPI project are intuitive.
2. **Searching by filename**:
   - If I know a file is named `user_service.py`, searching for it is straightforward.
   - Tools like `grep` or IDE search for function/class names (e.g., `UserService`) work well for finding definitions.
3. **Following imports**:
   - If I’m in `routers/user.py` and see `from services.user_service import UserService`, I can quickly jump to `services/user_service.py`.

**What feels like a workaround:**
1. **Flattening hierarchies for cross-cutting concerns**:
   - Logging, utilities, or config files are often dumped into `utils/` or `config/`, even if they’re used across the entire codebase. This makes it hard to know where to put or find them.
   - Example: Where does `utils/logging.py` belong? It’s not "user" or "order" specific, so it ends up in a generic `utils/` folder.
2. **Searching for usage or references**:
   - Finding all places where a function like `UserService.get_user()` is called requires a global search, which can be noisy (e.g., false positives from comments or variable names).
   - There’s no easy way to see "all files that depend on this file" without manually tracing imports.
3. **Temporal or conceptual relationships**:
   - If a file was renamed or split (e.g., `user.py` → `user_model.py` and `user_schema.py`), there’s no trace of this in the filesystem. You have to rely on Git history or comments.
   - Files that are related conceptually but not by imports (e.g., `models/user.py` and `frontend/src/UserForm.js`) have no link in the filesystem.
4. **Ambiguous or inconsistent naming**:
   - Files like `helpers.py`, `utils.py`, or `common.py` often become dumping grounds for unrelated functions. It’s hard to know what’s inside without opening them.
   - Example: `utils/string.py` might contain both generic string helpers and user-specific formatting functions.

**What I’d do differently without a directory tree:**
1. **Tag-based organization**:
   - Instead of folders, files could have tags like `#user`, `#auth`, `#database`, `#frontend`, `#util`, etc. This would let a file belong to multiple categories (e.g., `user_service.py` could have `#user` and `#service`).
   - Example: Search for all files with `#user` and `#api` to find user-related API routes.
2. **Dependency graph navigation**:
   - Show a graph of "files that import this file" or "files that this file depends on." This would make it easier to see ripple effects of changes.
   - Example: Click on `models/user.py` to see all files that import it (e.g., `services/user_service.py`, `schemas/user.py`).
3. **Temporal view**:
   - See how files have changed over time, with annotations for major refactors or splits. Example: "This file was split into two in commit `abc123`."
4. **Conceptual clusters**:
   - Group files by concept (e.g., "User Management" cluster includes `models/user.py`, `services/user_service.py`, `routers/user.py`, `frontend/src/UserForm.js`).
   - Example: A "User" cluster would show all files related to users, regardless of their directory.
5. **Search by usage or impact**:
   - Instead of searching for filenames or text, search for "files that call this function" or "files that depend on this database model."
   - Example: "Show me all files that would be affected if I change the `User` model."
