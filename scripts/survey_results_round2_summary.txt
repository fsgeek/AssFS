## Q1: Information hardest to reconstruct after context reset

**Architectural intent and constraints** — not the code itself, but *why* it's structured that way.

Specific example: I might rediscover that a codebase has separate `api/` and `internal/` modules by reading imports. But reconstructing *why* that boundary exists (security boundary? historical migration? performance isolation?) requires reading commit messages, READMEs, or asking the human again.

**Patterns I've internalized about a specific codebase** are also hard to reconstruct:
- "This project uses a custom config system instead of environment variables"
- "Error handling here uses exceptions; over there it uses Result types"
- "This module is being deprecated but still has 3 active callsites"

These feel like they should be documented but aren't, and I have to re-learn them.

**What's actually easy to reconstruct**: file locations, function signatures, basic dependency graphs. Those are in the code itself.

## Q2: How I mentally organize codebase relationships

When I work through a codebase, I build something like a **layered graph**:

- **Dependency layer**: "A imports from B imports from C" — fairly mechanical
- **Concept layer**: "These 5 files all deal with authentication" — requires reading code and inferring purpose
- **Constraint layer**: "These modules can't import each other (circular), so they depend on this shared interface" — requires understanding design decisions
- **Risk/change layer**: "Modifying X will cascade to Y and Z" — requires understanding both code and intent

If I could externalize this, it might look like a **directed graph with labeled edges and annotations**:
```
auth_service -> (imports) -> crypto_utils
auth_service -> (implements_interface) -> AuthProvider
auth_service -> (circular_risk) -> session_manager
```

But more importantly, I'd want **annotations on nodes**: "This module is stable/deprecated/experimental. This is a public API/internal. This was added for reason X."

What I actually do: I keep a mental model that degrades as context fills up. I'll have a clear picture of 3-4 modules, then it gets fuzzy.

## Q3: Important relationships with no natural place in the filesystem

**Temporal/migration relationships**: "This old module is being replaced by that new one. These 5 files need to be updated when the migration completes." There's no place to record this except in a PR description or issue tracker.

**Constraint relationships**: "These two modules must not import each other, even though the code doesn't prevent it." The filesystem has no way to express this. You'd need a linter rule or documentation.

**Ownership/responsibility**: "This file is maintained by team X. That file is a dependency that team Y owns." The code doesn't encode this. It matters for communication but lives in a wiki or CODEOWNERS file.

**Deprecated-but-used**: "This function is marked @deprecated but still has 7 callsites in production, and we can't remove it yet." The deprecation decorator exists, but the "can't remove yet" and "7 callsites" facts are scattered across issues and PRs.

**Conceptual groupings that cross directory boundaries**: "These 12 files together implement the search feature, but they're scattered across `api/`, `models/`, `utils/`, and `ui/`." The filesystem groups by technical layer; the feature concept lives elsewhere.

## Q4: Navigation experience — natural vs. workaround

**Feels natural:**
- `ls` to explore structure
- `grep` or search to find where a symbol is used
- Reading a file top-to-bottom
- Following imports to understand dependencies

**Feels like workaround:**
- Finding all files related to a *concept* (requires grepping for keywords or reading multiple docs)
- Understanding *why* a file is in a particular directory (requires reading READMEs or commit history)
- Discovering that two distant files are related (requires reading both and inferring connection)
- Navigating "sideways" — "show me all files that import from X" requires tool support, not native filesystem capability

**What I'd do differently**: I'd want the filesystem to support **semantic queries**, not just path queries:
- "Show me all files implementing AuthProvider"
- "Show me all files modified to support feature X"
- "Show me all files that can't import each other"

Currently I'm constrained to: "Show me files matching this path pattern or name pattern or text pattern."

The directory tree is fundamentally **hierarchical and static**. A codebase's actual structure is **graph-like and evolving**.

## Q5: What to persist between sessions

**Ranked by value:**

1. **A map of the codebase's semantic structure** — "Here are the major modules, here's what each does, here are the key interfaces." Not the code itself (that's in git), but the *conceptual map*. When I restart, I spend 30 minutes re-reading to rebuild this.

2. **Open questions and uncertainties** — "I don't understand why X is implemented this way" or "This looks like a bug but I'm not sure." Capturing these saves me from re-discovering the same confusion.

3. **Callsite analysis** — "Function X is called from these 7 places." I often have to recompute this.

4. **Change impact analysis** — "Modifying Y will affect these files." Related to above.

5. **Architectural constraints** — "Don't import from X into Y" or "This module is frozen/deprecated."

**How I'd want to find it**: By asking questions in natural language, or by navigating a structured map. Not by filename or path. "What do I need to know about authentication?" rather than "find auth.md".

## Q6: Sharing information across multiple agents

**Most valuable to share:**

1. **Architectural decisions and constraints** — "We're moving to this new pattern" or "Don't touch this module, it's under refactor." This prevents agents from working at cross-purposes.

2. **Task-specific context** — "Agent A is currently refactoring module X. Don't modify its dependencies yet." Coordination.

3. **Analysis results** — "Here are all the callsites of function Y" or "Here's the dependency graph." This is expensive to recompute and valuable to share.

4. **Learned patterns** — "In this codebase, error handling uses Result types, not exceptions." Speeds up other agents' work.

**How I imagine it working:**

- A **shared knowledge base** (not files, but structured data) that agents can read and append to
- **Locking/coordination primitives** — "Agent A has claimed responsibility for module X until timestamp T"
- **Queries** — agents can ask "what's the current status of module X?" and get a recent answer
- **Annotation layer** — separate from code, but queryable alongside it

What I *don't* want: agents leaving comments in code or scattered notes. That's fragile and hard to query.
